ARDUINO QUICK-DRAW DUEL

This project is insipired by the internet trend of running the game DOOM on uncanny and often hilarious platforms (see doom running on an osciloscope). In this project ive made my own game with the end goal of having it run on the smallest possible device, which i predict will be approx. 40mm x 20mm or smaller. The game is a "Cowboy Simulator" reaction speed game with custom made, albeit very simple sprites. You can play the game here on wokwi (note this is a free program and servers often clog the ability to run projects).

StatusCompleted TypePersonal project ToolsArduino Nano, C++, Adafruit GFX and SSD1306 libraries

Project introduction

Cowboy Simulator is a one-button duel against the ATmega328 arduino chip. After a random number of paces both cowboys turn, and the player has to fire before the bot does. Fire while still walking and the game ends in dishonour.

Major design choices

  • Non-blocking timing with millis(). delay() stops the processor, so a button press during a tune would be missed, which ruins a reaction game. A small note scheduler plays each tune note by note while the loop keeps checking the button.
  • State machine. Seven states (start, walking, duel, win, lose, tie and false start) keep each screen’s logic separate, so adding an outcome means adding one state.
  • Graphics stored in flash. The six cowboy frames and the title screen take 1,088 bytes, over half the Nano’s 2 KB of RAM. Kept in flash with PROGMEM, they use none.
  • 128 × 32 OLED over I2C. Two signal wires, and a 512-byte screen buffer. A 128 × 64 panel would need twice the RAM for the same game.
  • Bot fires 200–400 ms after the turn. That is around typical human reaction time, so the bot can be beaten, but rarely by luck.

  • Song engine: each tune is a list of {frequency + duration} notes, with 0 Hz as a rest. Every loop checks millis() and moves to the next note when the current one is due.
  • Debounce: a press only counts if 200 ms have passed since the last, so switch bounce can’t register twice.
  • Accurate timing in the duel: nothing is redrawn while waiting for a shot, so each loop only reads the button and updates the buzzer. A screen update over I2C takes milliseconds and would delay the reading.
  • Random pace count: the turn comes after 3 to 5 paces, so the player can’t count ahead and fire on a rhythm. A countdown above the cowboys shows the paces left.
  • Result over the final pose: the result text is printed on top of the last frame instead of a blank screen, so the player sees who was hit.

Results

  • Program size: 20.0 KB of the Nano’s 30 KB of program space (65 %) and 717 bytes of global variables (35 % of RAM), plus the 512-byte screen buffer made at start-up. That leaves about 800 bytes of RAM free.
  • Game function: Simulations of the games functionality is succesful and PCB development is ready to begin.

Future developments

  • PCB development: PCB size will likely be not much larger than the OLED screen, as the ATmega328P only has 6 pins in use, 2 of these being 5V and ground.
  • Reaction time/score: Print the playes draw time on the result screen.
  • Difficulty levels: There is room to implement a potentiometer to set the diffuculty level (bot draw time).
  • Power system: A power system is yet to be developed, this system will require a small battery, and likely a converter to power the chip.
